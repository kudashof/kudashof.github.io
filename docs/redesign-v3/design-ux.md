# Дизайн и UX — Variant 3

Источник: [Google Doc](https://docs.google.com/document/d/1dBQ2rKSfVM6htgc95J7VGnSwyU84Dl7yKnmdHG1hOag/edit). Снимок документа от 2026-09-30; этот файл — локальная копия для разработки.

**Текущий статус:** Алексей уточнил 2026-09-30, что макет ещё в разработке. Формулировки исходного документа об «утверждённом макете» ниже относятся к ранее выбранному направлению Variant 3 и не означают финального утверждения визуального файла. См. [manifest.json](manifest.json).

## 1. Решение
Рабочая база: утверждённый Variant 3. Его визуальный язык и цвета сохраняются. Variant 3.1 по цветам отклонён и не является источником палитры.


## 2. Принцип развития
Не делать новый редизайн поверх уже выбранного дизайна. Улучшение должно происходить через motion, интерактивный ритм, глубину, микроинтеракции и аккуратное поведение элементов.


## 3. Источник истины
Приоритет источников:
1) утверждённый макет Variant 3;
2) реальные ассеты и текущий контент сайта;
3) этот документ;
4) технические решения Codex.
Если между ними конфликт, Variant 3 определяет визуальную сторону, а реальный контент - фактическую.


ВАЖНО: точные HEX/RGB, гарнитуры и размеры из макета Variant 3 в этом чате недоступны. Они не были выдуманы. Codex должен извлечь их из доступного утверждённого макета/ассетов. Если такого источника в репозитории нет, реализацию финальной стилизации необходимо остановить до получения макета.


## 4. Визуальная система
Цвета описывать semantic tokens:
- bg-primary / bg-secondary
- surface-primary / surface-elevated
- text-primary / text-secondary / text-muted
- accent-primary / accent-secondary
- border-subtle / border-strong
- state-success / state-warning / state-error, если нужны.
Значения токенов берутся только из Variant 3. Не заимствовать палитру Variant 3.1.


## 5. Типографика
- Hero/display: сильный визуальный акцент, но без ухудшения читабельности на mobile.
- H1-H3: ясная ступенчатая иерархия.
- Body: комфортная длина строки и межстрочный интервал.
- Caption/meta: не конкурирует с основным текстом.
- Buttons/controls: текст остаётся читаемым при всех состояниях.
Если точная гарнитура Variant 3 доступна - использовать её. Если нет - не подменять молча, а зафиксировать fallback.


## 6. Layout
- Один основной контейнерный принцип по всему сайту.
- Секциям нужен различимый ритм, а не одинаковая высота и одинаковые отступы.
- Hero должен быстро объяснять, куда пользователь попал и какое главное действие.
- Декор не должен закрывать CTA, заголовки, изображения или навигацию.
- На узких экранах композиция перестраивается, а не просто масштабируется.


## 7. Компоненты
Минимальный набор для инвентаризации и реализации:
- Header / navigation / mobile menu.
- Hero и декоративные элементы hero.
- Primary / secondary / ghost CTA.
- Карточки или элементы списков.
- Заголовки секций.
- Медиа-блоки.
- Формы и поля ввода, если есть на текущем сайте.
- Footer.
- Системные состояния: loading, empty, error, success, если присутствуют.


Для интерактивных компонентов проверить normal / hover / focus-visible / active / disabled. Hover не должен быть единственным способом понять интерактивность.


## 8. Responsive
Desktop:
- Максимальная выразительность декора и motion.
- Можно использовать более глубокий параллакс и пространственные эффекты, но без scroll-jacking.


Tablet:
- Снижать количество одновременно движущихся слоёв.
- Сохранять композиционный приоритет контента.


Mobile:
- Touch-first.
- Упростить параллакс и крупные фоновые перемещения.
- Не использовать эффекты, требующие hover.
- Главный CTA остаётся легко достижимым и визуально понятным.
- Проверить 320, 360, 390/393, 430 px как практические контрольные ширины, плюс реальные breakpoints текущего проекта.


## 9. UX
- Первое экранное состояние должно давать смысл до того, как пользователь начинает скроллить.
- Главный CTA не должен быть спрятан анимацией.
- Навигация предсказуема.
- Анимация подтверждает действие пользователя, а не заменяет обратную связь.
- Не добавлять карусели, сложные drag-механики и скрытые жесты без продуктовой причины.


## 10. Accessibility
- Цель WCAG 2.2 AA.
- Видимый focus-visible.
- Управление клавиатурой для навигации и интерактивных компонентов.
- Семантическая структура heading levels.
- Alt для значимых изображений, декоративные изображения исключать из accessibility tree.
- Не полагаться только на цвет для статусов.
- Интерактивные цели не должны становиться микроскопическими на mobile.
- Полная поддержка prefers-reduced-motion.


## 11. Performance budget
Целевые полевые ориентиры:
- LCP <= 2.5 s.
- INP <= 200 ms.
- CLS <= 0.1.
Не использовать motion-эффект, если ради него приходится ухудшать эти показатели.


## 12. Что НЕ делать
- Не применять цвета Variant 3.1.
- Не делать новый визуальный концепт вместо Variant 3.
- Не превращать страницу в демонстрацию анимационного движка.
- Не делать scroll-jacking.
- Не блокировать контент прелоадером ради эффекта.
- Не ставить тяжёлые видео/канвас/WebGL только потому, что это выглядит технологично.
- Не менять тексты, структуру URL и SEO-смысл без отдельной причины.


## 13. Acceptance
Сайт считается визуально принятым, когда:
- при первом взгляде он узнаётся как Variant 3;
- цвета не уплыли в 3.1;
- движение делает интерфейс современнее, но контент читается без борьбы;
- мобильная версия выглядит спроектированной отдельно, а не ужатой;
- без анимации интерфейс остаётся полноценным;
- нет заметного скачка layout во время загрузки.
