# Ворота реализации и выпуска

## Definition of Ready

Инициатива готова к решению о конкретном scope, когда:

- сформулирована одна пользовательская проблема, а не перечень экранов;
- объяснено, почему текущий продукт её не решает;
- задан минимальный scope и явно записано, что не входит;
- известны источник данных, его ограничения и обязательная атрибуция;
- описаны основной сценарий и loading/empty/error/retry;
- определены мобильное поведение, клавиатура, фокус и прямые ссылки;
- есть наблюдаемый сигнал пользы и стоп-условие;
- перечислены риски, способ отката и зависимости;
- записано конкретное решение, которое должен принять Алексей.
- исследование отделяет подтверждённые факты от неизвестного, а в спецификации указаны альтернатива без новой функции и цена поддержки.

До явного решения Алексея новая идея остаётся в [CANDIDATES.md](CANDIDATES.md). `decisionScope: research` разрешает исследование, но не реализацию UI; `decisionScope: implementation` относится только к записанному scope.

## Definition of Done для реализации

### Код и данные

- Реализован только утверждённый scope.
- URL и Back/Forward сохраняют релевантное состояние.
- Запросы корректны для `movie` и `tv`, если функция поддерживает оба типа.
- Устаревшие запросы отменяются или не влияют на текущий экран.
- Новые структуры localStorage и импортируемые данные валидируются и версионируются.
- Нет новых секретов, персональных данных или неутверждённых внешних отправок.

### Состояния интерфейса

- Проверены loading, content, empty, error и retry.
- Проверены отсутствие постера, длинное название, отсутствующее описание и неполный ответ API.
- Основной сценарий работает мышью, касанием и клавиатурой; фокус после открытия/закрытия предсказуем.
- Светлая и тёмная темы не теряют читаемость.

### Автоматические проверки

- `npm run check` завершён с кодом 0.
- `npm test` завершён с кодом 0.
- Добавлены тесты преобразования данных, URL и ошибочных входов, относящиеся к функции.
- `git diff --check` не сообщает пробельных ошибок.
- Для изменённого сценария в [SCENARIOS.md](SCENARIOS.md) указаны применимые проверки, а фактические результаты записаны отдельно в [EVIDENCE.md](EVIDENCE.md).

### Ручная проверка до merge

- Desktop Safari и один Chromium-браузер: основной сценарий, refresh, Back/Forward, прямая ссылка.
- Узкий viewport: нет обрезанных действий, перекрытий и горизонтального скролла.
- Реальный iPhone Safari: клавиатура, прокрутка, safe area, открытие карточки, возврат без потери состояния.
- PWA с домашнего экрана: запуск в установленном режиме и понятное поведение без сети.

Эмуляция мобильного viewport помогает найти ошибки, но не заменяет реальный iPhone Safari.

## Ворота публикации

После разрешённого merge в `master`:

1. Зафиксировать commit и результат GitHub Pages.
2. Открыть публичный HTTPS-адрес и проверить реально загруженную версию оболочки. Если старая версия остаётся, разбирать обновление service worker без очистки пользовательских данных.
3. Проверить новый сценарий и один существующий критический путь: «Подбор → карточка → назад».
4. Проверить консоль, запросы, прямую ссылку и отсутствие регрессии «Моё».
5. Только после этого повысить `delivery` до `public_verified` и записать дату и доказательство. `acceptance: passed` ставить отдельно после всех применимых ручных сценариев; сборка Pages сама по себе означает только `pages_built`.

## Откат

- Предпочитать функцию, которую можно выключить удалением одного блока/конфига без миграции данных.
- Не удалять локальные пользовательские данные при откате UI.
- Если выпуск нарушает основной путь, вернуть предыдущий рабочий commit отдельным безопасным изменением; force push и переписывание `master` не использовать.
