# Харнес развития MovieDB

Харнес связывает пользовательскую проблему, исследование, решение Алексея, реализацию и проверяемый результат. Он хранится рядом с кодом, но не заменяет Pull Request и тесты.

## Зачем он нужен

Харнес помогает проверить пользу и границы новой идеи до реализации. Отдельные состояния показывают, что уже написано и опубликовано, а что ещё требует приёмки.

Главная продуктовая цель ближайших улучшений:

> Сократить путь от «не знаю, что посмотреть» до обоснованного выбора и облегчить возвращение к выбранному фильму или сериалу.

## Четыре независимых состояния

`manifest.json` использует `schemaVersion: 2`. Старый общий `status` удалён: он не мог одновременно показать публикацию функции и открытую физическую приёмку.

| Поле | Значение |
| --- | --- |
| `decision` и `decisionScope` | Одобрено исследование или реализация конкретного scope |
| `implementation` | `not_started`, `in_progress`, `done` — состояние кода |
| `delivery` | `none`, `branch`, `pr`, `master`, `pages_built`, `public_verified` — на каком уровне доказан выпуск |
| `acceptance` | `not_applicable`, `pending`, `passed` — выполнены ли применимые ручные проверки |

`pages_built` означает успешный ответ GitHub Pages о сборке. Это не проверка публичного сценария на iPhone. `public_verified` требует отдельной проверки публичного URL. `acceptance: pending` может сосуществовать с опубликованным кодом: перенос физической проверки для пакета 7 октября не отменил её. Значения в кратком заголовке спецификации зеркалируют `manifest.json`; валидатор сверяет их. Старое поле `Статус решения` в тексте спецификации зеркалирует только `decision`.

Приоритеты существующих инициатив относятся к их утверждённым спецификациям и не образуют новую очередь разработки. Кандидаты из [`CANDIDATES.md`](CANDIDATES.md) не входят в `manifest.json` до отдельного решения Алексея о реализации конкретного scope.

## Как работать с харнесом

1. Описать проблему, более дешёвую альтернативу и неизвестное в [`RESEARCH.md`](RESEARCH.md). Идея остаётся кандидатом до решения о конкретном scope.
2. Записать способ проверки пользы и стоп-условие в [`EXPERIMENTS.md`](EXPERIMENTS.md). План эксперимента не равен проведённому исследованию.
3. Подготовить спецификацию по [`FEATURE-TEMPLATE.md`](FEATURE-TEMPLATE.md) и записать точное решение Алексея с его объёмом.
4. После разрешённой реализации вести четыре состояния в `manifest.json`, факты — в [`EVIDENCE.md`](EVIDENCE.md), сценарии — в [`SCENARIOS.md`](SCENARIOS.md). Запустить `npm run check:harness`.
5. Пройти [`RELEASE-GATES.md`](RELEASE-GATES.md). Merge в `master` и публикация требуют отдельного разрешения; согласие на расширение харнеса таким разрешением не является.

Алексей утвердил расширение харнеса 11 октября 2026 года. Новые функции разрешено описать как кандидатов, без реализации и публикации.
