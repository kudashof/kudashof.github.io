# Харнес развития MovieDB

Этот каталог — единый контур, по которому новая идея проходит путь от гипотезы до проверенного выпуска. Он не заменяет код, GitHub Issues или Pull Request: он связывает продуктовую задачу, решение владельца, границы реализации и доказательства готовности.

## Зачем он нужен

Без харнеса идея легко превращается в код раньше, чем понятны пользовательская польза, данные, мобильные состояния и цена поддержки. Харнес делает статус каждой инициативы явным и не позволяет назвать функцию готовой только потому, что она написана или прошла локальные тесты.

Главная продуктовая цель ближайших улучшений:

> Сократить путь от «не знаю, что посмотреть» до обоснованного выбора и облегчить возвращение к выбранному фильму или сериалу.

## Жизненный цикл инициативы

```text
idea → researched → ready_for_decision → approved → in_progress
     → verified → released
```

Дополнительные конечные состояния: `paused` и `rejected`.

- `idea` — записана проблема, но данных для решения ещё нет.
- `researched` — проверены источник данных, ограничения и основные альтернативы.
- `ready_for_decision` — понятны scope, риски и критерии; нужно решение Алексея.
- `approved` — Алексей утвердил конкретный scope. Только после этого создаётся реализационная задача.
- `in_progress` — есть рабочая ветка и исполнитель.
- `verified` — выполнены автоматические и ручные проверки, но production ещё не доказан.
- `released` — изменение есть в `master`, GitHub Pages успешно собран, публичный URL проверен.
- `paused` — работа сознательно остановлена до указанного условия.
- `rejected` — принято решение не делать инициативу в этом виде.

Статус нельзя повышать задним числом по одному факту. Например, локальный код не означает `verified`, а merge в `master` не означает `released` без проверки GitHub Pages.

## Как работать с харнесом

1. Создать спецификацию по [`FEATURE-TEMPLATE.md`](FEATURE-TEMPLATE.md).
2. Добавить инициативу в `manifest.json` со статусом `idea` или `researched`.
3. Запустить `npm run check:harness`.
4. Довести спецификацию до `ready_for_decision`: заполнить пользу, scope, состояния, риски, проверки и требуемое решение.
5. После явного решения Алексея записать его в спецификацию и изменить статус на `approved`.
6. Реализовывать одну ограниченную инициативу в отдельной ветке и PR.
7. Пройти [`RELEASE-GATES.md`](RELEASE-GATES.md), приложив факты по каждому уровню: код, тесты, ручная проверка, remote/PR, GitHub Pages, публичный сайт.
8. После проверки публичного адреса изменить статус на `released` и записать доказательство в спецификацию.

## Текущая граница

Уже выпущенные PWA и локальное «Моё» описаны в основных документах проекта. Пять инициатив в этом харнесе — следующий возможный этап, но ни одна из них ещё не считается утверждённой реализацией.

Харнес хранится рядом с кодом, чтобы изменения требований проходили обычный review. `manifest.json` — источник истины для статусов; тексты спецификаций объясняют причины и критерии.
